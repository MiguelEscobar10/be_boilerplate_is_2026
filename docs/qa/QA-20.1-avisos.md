## Backend: casos automatizados

Archivo: [`test/qa/qa-20.1-avisos.e2e-spec.ts`](../../test/qa/qa-20.1-avisos.e2e-spec.ts).

La prueba usa el servicio como lo haría otro módulo. Importa `AvisosService`,
`AvisoInvalidoError` y `ModuloOrigen` solo desde `@Notifications`, como pide el
[contrato](../contratos/servicio-avisos.md), y llama a `notificar` desde la
app completa, conectada a la base `_test`. Revisa el resultado en dos lugares:

- **La base:** conteo de filas en `notifications`.
- **La bandeja de H10:** `GET /api/v1/notificaciones` y
  `GET /api/v1/notificaciones/no-leidas/conteo`, con el JWT del destinatario
  sacado de un login real.

Hay dos usuarios: A (arrendador) y B (arrendatario).

- **En cada aviso válido** se comprueba que aparece en la bandeja del
  destinatario como no leído y con la forma documentada del item, que su conteo
  de no leídas sube 1 y que **no** aparece en la bandeja del otro usuario.
- **En cada aviso inválido** se comprueba que se lanza `AvisoInvalidoError` con
  `codigo: 'AVISO_INVALIDO'` y el `campo` del contrato, que el conteo de filas
  no cambia y que el conteo de no leídas tampoco.

### Criterios de H20 que cubre cada caso

| Criterio | Casos |
|---|---|
| 1. Un aviso válido se registra para ese destinatario y aparece en su bandeja como no leído | C01 a C04, C14 a C19 |
| 2. La referencia es opcional: si viene se guarda, y sin ella se registra igual | C01, C02 |
| 3. Los ejemplos del contrato por módulo emisor usan los mismos campos y la misma lista de módulos, y el aviso queda en la bandeja | C14 a C19 |
| 4. Sin destinatario o sin título no se registra y quien llama recibe `AvisoInvalidoError` | C05 a C09 (C10 cubre el mensaje) |
| 5. Con un módulo de origen fuera de la lista o un destinatario inexistente no se registra | C11, C12 |
| Técnico: los avisos inválidos no dejan filas (conteo en la base) | C05 a C12 |
| Técnico: no se puede llamar desde el exterior | C20, C21 |

En C14 a C19, el criterio 3 se revisa con las funciones de
[`test/contratos/servicio-avisos.ejemplos.ts`](../../test/contratos/servicio-avisos.ejemplos.ts),
que son copia exacta de los bloques del contrato (lo verifica
`servicio-avisos.contrato.spec.ts`). Se comprueban tres cosas: que el título es
el de la tabla de eventos del contrato, que `moduloOrigen` es un valor de
`ModuloOrigen` y que el item de la bandeja tiene los campos documentados.

## Cómo repetirlo

El helper de pruebas agrega `_test` al nombre de la base de `DATABASE_URL`, así
que son dos pasos con URL distintas:

```bash
# 1. Migraciones en la base de pruebas (URL que ya termina en _test)
DATABASE_URL="postgresql://postgres:postgres@localhost:5432/si_be_boilerplate_test?schema=public" npx prisma migrate deploy

# 2. Las pruebas, con la DATABASE_URL normal del .env (el helper usa ..._test)
#    o con TEST_DATABASE_URL apuntando directo a la base _test
npx vitest run --config ./vitest.config.e2e.ts test/qa/qa-20.1-avisos.e2e-spec.ts --reporter=verbose
```

En el paso 2, **no** dejes `DATABASE_URL` apuntando a la base `_test`: el
helper le agregaría otro `_test`. Los correos de prueba llevan un sufijo único
por ejecución (`qa-20.1-<uuid>@test.local`). Al terminar se borran esos
usuarios, y la cascada se lleva sus avisos.
